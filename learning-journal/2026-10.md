### What I Learned

#### Cryptography Basics

I developed a better understanding of cryptography and its role in cybersecurity. Cryptography is used to protect information from unauthorized access and helps provide confidentiality, integrity, authentication, and non-repudiation.

I learned the difference between plaintext and ciphertext and how encryption transforms readable information into an unreadable format using a cryptographic algorithm and key.

I also studied symmetric encryption, where the same secret key is used to encrypt and decrypt information. Symmetric encryption is efficient for protecting large amounts of data, but securely exchanging the secret key between parties can present a challenge.

This helped me understand that cryptography is not simply about hiding information; it is an important part of securing communications, stored data, authentication systems, and many other technologies.

#### Public Key Cryptography Basics

I studied asymmetric, or public key, cryptography and learned how it differs from symmetric encryption.

Instead of using one shared secret key, asymmetric cryptography uses a pair of mathematically related keys:

- **Public key** — can be shared with others.
- **Private key** — must remain protected by its owner.

I learned that public key cryptography can be used for secure key exchange, authentication, encryption, and digital signatures.

I also developed a better understanding of how asymmetric and symmetric encryption can work together. Public key cryptography can help establish or exchange secret information securely, while symmetric encryption can then efficiently protect larger amounts of data.

This gave me greater insight into the cryptographic concepts behind technologies such as HTTPS, TLS, SSH, certificates, and secure online communication.

#### Hashing Basics

I learned that hashing is different from encryption.

A cryptographic hash function takes input data and produces a fixed-size output known as a hash or digest. Unlike encryption, hashing is designed to be a one-way process and is not intended to be reversed to recover the original information.

I studied how hashes can be used to verify data integrity. If even a small part of a file or message changes, its resulting hash should also change, allowing modifications to be detected.

I also learned how hashing is used in password storage. Instead of storing passwords directly as plaintext, systems can store password hashes and compare them during authentication.

I learned about the importance of techniques such as salting passwords, which helps make attacks using precomputed hash databases more difficult.

This topic demonstrated why secure password storage requires more than simply applying a basic hash function.

#### John the Ripper Basics

I gained introductory hands-on experience with John the Ripper, a password auditing and recovery tool.

Using authorized TryHackMe lab environments, I learned how John the Ripper can test password hashes against possible passwords and demonstrate the risks associated with weak passwords.

I practised working with hash data, using wordlists, and interpreting the results produced by the tool.

This exercise demonstrated that even when passwords are stored as hashes, weak or predictable passwords may still be discovered through password-cracking techniques.

John the Ripper also helped connect the theoretical concepts I learned about hashing with a practical cybersecurity use case.

### Hands-On Practice

During the TryHackMe labs, I applied the cryptography concepts through practical exercises.

My activities included:

### Challenges

One challenge was distinguishing between encryption, encoding, and hashing because they can initially appear to perform similar transformations on data. I now understand that they have different purposes and security properties.

Another challenge was understanding how public and private keys interact in different situations. Continued practice with certificates, SSH, and TLS should help reinforce these concepts.

Working with password hashes also required careful attention to hash formats and the tools used to process them. I would like to continue practising hash identification and password auditing in legal training environments.

### Key Takeaways

My biggest takeaway from this module is that cryptography provides several different mechanisms for protecting information, and each mechanism serves a different purpose.

**Symmetric encryption** provides efficient encryption using a shared secret key, while **asymmetric encryption** uses public and private keys and enables capabilities such as secure key exchange and digital signatures.

**Hashing** is designed to produce a one-way representation of information and is useful for integrity verification and secure password-storage systems.




I also learned through John the Ripper that cryptographic protection cannot compensate for weak passwords. Strong password practices and secure password-storage techniques remain important parts of an organization's security.

Understanding these concepts gives me a stronger foundation for studying authentication, TLS/HTTPS, certificates, digital signatures, password security, vulnerability assessment, and security monitoring.

**HTTP methods studied:**

| Method | Purpose |
|---|---|
| GET | Retrieve information from a server |
| POST | Submit data for processing |
| PUT | Create or replace a resource |
| PATCH | Partially modify a resource |

**HTTP security concepts:**

I learned about several headers and directives that help protect web applications:

- `Host` — identifies the requested server.
- `Content-Type` — identifies the format of transmitted data.
- `Server` — may reveal web server software information.
- `Secure` — restricts cookie transmission to HTTPS connections.
- `HttpOnly` — prevents JavaScript from directly accessing protected cookies.
- `Content-Security-Policy` — restricts permitted content sources.
- `script-src` — controls which sources may provide executable scripts.
- `Strict-Transport-Security` — instructs browsers to use HTTPS.
- `includeSubDomains` — extends HSTS protection to subdomains.
- `X-Content-Type-Options: nosniff` — prevents certain MIME-type sniffing behaviours.

**Practical exercise: HTTP requests**

I explored how API endpoints respond to different HTTP methods.

Example requests:

```http

```

```http

Content-Type: application/json

{"country":"US"}
```

```http
DELETE /api/user/1 HTTP/1.1

```

These examples helped reinforce the difference between retrieving, updating, and deleting application data.

**Security takeaway:** Understanding HTTP communication is essential for identifying suspicious requests, insecure configurations, and web application vulnerabilities.

#### D. Burp Suite: The Basics

I was introduced to Burp Suite, a web application security testing platform used to inspect and manipulate HTTP traffic in authorized testing environments.

**Key learning points:**

**Burp Suite components:**

| Component | Purpose |
|---|---|
| Proxy | Intercepts and inspects HTTP/HTTPS traffic |
| HTTP History | Records observed requests and responses |
| Repeater | Allows controlled modification and resending of requests |
| Intruder | Automates repeated request variations |
| Decoder | Encodes and decodes data |
| Comparer | Compares requests or responses |

**Example testing workflow:**

1. Open Burp Suite and use its configured browser.
2. Enable interception in the Proxy tab.
3. Navigate to an authorized test application.
4. Capture an HTTP request.
5. Examine the method, URL, headers, and body.
6. Send the request to Repeater.
7. Modify a non-destructive test parameter.
8. Observe and compare the server's response.

**Example request:**

```http

Host: lab.example
```

By examining requests and responses, I developed a better understanding of how security testers investigate application behaviour.

### 2. What I Learned

#### A. Hydra — Password Auditing and Authentication Security

I studied Hydra, a command-line password auditing tool used to assess the security of authentication services.

**Key learning points:**

- Understanding password attacks and the risks associated with weak credentials.
- Learning the difference between brute-force and dictionary attacks.
- Understanding how Hydra tests authentication credentials against supported services.
- Recognizing the importance of selecting the correct authentication protocol.
- Understanding how account lockout policies, rate limiting, and multifactor authentication reduce password attack risks.
- Learning why password auditing must be restricted to authorized accounts and systems.

**Important concepts:**

| Concept | Explanation |
|---|---|
| Brute-force attack | Attempts many possible passwords |
| Dictionary attack | Tests passwords from a predefined list |
| Credential stuffing | Attempts credentials exposed in previous breaches |
| Authentication service | Verifies a user's identity |
| Rate limiting | Restricts repeated authentication attempts |
| Account lockout | Temporarily blocks access after repeated failures |
| MFA | Requires an additional authentication factor |

**Commands studied:**

```bash
hydra -h
hydra -U ssh
```

The first command displays Hydra's help information, while the second provides usage information for its SSH module.

**Authorized lab example:**

```bash
hydra -l labuser -P ./lab-passwords.txt \
  -t 1 -f ssh://192.0.2.10
```

**Command explanation:**

- `-l labuser` specifies the training account.
- `-P ./lab-passwords.txt` supplies a small, instructor-approved password list.
- `-t 1` limits the test to one concurrent task.
- `-f` stops after a valid credential is identified.
- `ssh://192.0.2.10` identifies the authorized laboratory SSH service.

The IP address is illustrative and must be replaced with the assigned lab target.

**Security takeaway:** Weak passwords and poorly protected authentication systems can create significant security risks. Strong passwords, MFA, monitoring, and rate limiting are essential defensive measures.

#### B. Gobuster — Web Directory and Resource Enumeration

I studied Gobuster, a command-line enumeration tool used to discover web directories, files, virtual hosts, and DNS names.

**Key learning points:**

- Understanding why attackers and penetration testers enumerate web applications.
- Learning how wordlists support resource discovery.
- Understanding directory and file enumeration.
- Recognizing how HTTP status codes help interpret results.
- Understanding the risks associated with exposed administrative interfaces, backup files, and sensitive directories.
- Learning why enumeration results require manual validation.

**Important concepts:**

| Concept | Explanation |
|---|---|
| Enumeration | Collecting detailed information about a target |
| Wordlist | Collection of possible names or paths |
| Directory discovery | Identifying accessible web paths |
| Virtual host | Website hosted under a particular hostname |
| HTTP 200 | Request succeeded |
| HTTP 301/302 | Resource redirects elsewhere |
| HTTP 403 | Access forbidden |
| HTTP 404 | Resource not found |

**Commands studied:**

```bash
gobuster --help
gobuster dir --help
gobuster dns --help
gobuster vhost --help
```

**Authorized lab example:**

```bash
gobuster dir \
  -u http://192.0.2.10/ \
  -w ./lab-directories.txt \
  -t 2
```

**Command explanation:**

- `dir` selects directory and file enumeration mode.
- `-u` specifies the assigned laboratory website.
- `-w` specifies the wordlist.
- `-t 2` limits concurrent requests to two threads.

**Example output:**

```text
/images     (Status: 301)
/admin      (Status: 403)
/robots.txt (Status: 200)
```

These are illustrative results, not findings from a specific TryHackMe target.

**What I learned from interpreting results:**

A successful response may indicate an accessible resource, while a `403` response can indicate that a path exists but access is restricted. Redirect responses require further investigation to understand their destination.

**Security takeaway:** Resource enumeration can reveal unnecessary exposure. Organizations should enforce access controls, remove sensitive backup files from web-accessible directories, and avoid relying on hidden paths as a security measure.

#### C. Shells Overview — Understanding Remote System Interaction

I studied the different types of command shells used during system administration, penetration testing, and incident response.

**Key learning points:**

- Understanding what a shell is and how it interacts with an operating system.
- Distinguishing between command shells and graphical interfaces.
- Learning the difference between bind shells and reverse shells.
- Understanding the role of listeners and network connections.
- Recognizing the difference between interactive and non-interactive shells.
- Understanding why unexpected shell processes and outbound connections can indicate compromise.

**Types of shells:**

| Shell type | Description |
|---|---|
| Command shell | Allows users to execute operating system commands |
| Bind shell | Listens for an incoming connection |
| Reverse shell | Initiates a connection to another system |
| Interactive shell | Supports direct command interaction |
| Non-interactive shell | Executes commands without a full interactive interface |
| Web shell | Provides command execution through a web application when deployed |

**Linux shell commands reviewed:**

```bash
whoami
hostname
pwd
id
uname -a
```

These commands identify the current user, system name, working directory, account privileges, and operating system information.

**Local shell demonstration:**

Terminal 1:

```bash
nc -l 127.0.0.1 4444
```

Terminal 2:

```bash
echo "Hello from the lab" | nc 127.0.0.1 4444
```

This demonstrates basic listener and client communication on the same machine without creating a remote command-execution session.

**Defensive indicators studied:**

- Unusual outbound connections.
- Command interpreters launched by web server processes.
- Unexpected shell activity under service accounts.
- Suspicious parent-child process relationships.
- Unrecognized network listeners.

**Security takeaway:** Understanding shell behaviour helps defenders recognize unauthorized remote access and investigate suspicious process and network activity.

#### D. SQLmap — SQL Injection Testing Fundamentals

I studied SQLmap, an automated tool used by penetration testers to assess SQL injection vulnerabilities in web applications.

**Key learning points:**

- Understanding what SQL injection is and why it occurs.
- Recognizing how unsafe handling of user input can affect database queries.
- Learning how SQLmap automates aspects of SQL injection testing.
- Understanding the importance of selecting specific test parameters.
- Learning why automated findings require careful validation.
- Understanding how prepared statements and least-privilege database accounts reduce SQL injection risks.

**Important concepts:**

| Concept | Explanation |
|---|---|
| SQL injection | Manipulation of database queries through unsafe input handling |
| Query parameter | Input value passed through a URL or request |
| Parameterized query | Separates SQL code from user-supplied values |
| Input validation | Checks input against expected rules |
| Least privilege | Limits database accounts to necessary permissions |
| Vulnerability verification | Confirms whether a reported weakness is genuine |

**Commands studied:**

```bash
sqlmap --help
sqlmap --version
```

**Authorized lab example:**

```bash
sqlmap -u "http://192.0.2.10/item?id=1" \
  -p id \
  --batch \
  --level=1 \
  --risk=1
```

**Command explanation:**

- `-u` identifies the assigned training URL.
- `-p id` selects the parameter to test.
- `--batch` accepts default responses to prompts.
- `--level=1` selects the lowest standard test level.
- `--risk=1` uses the lowest standard risk setting.

The command illustrates a basic authorized assessment; it does not imply that a vulnerability was discovered.

**Secure coding example:**

```python
cursor.execute(
    "SELECT * FROM users WHERE id = %s",
    (user_id,)
)
```

This illustrates a parameterized SQL query using a database driver that supports `%s` placeholders.

Parameterized queries help prevent untrusted input from being interpreted as executable SQL.

**Security takeaway:** SQL injection vulnerabilities can expose sensitive data or compromise application functionality. Secure coding, least privilege, and regular security testing are essential preventive controls.
