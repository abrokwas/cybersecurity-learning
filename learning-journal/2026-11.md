#### C. Digital Forensics Fundamentals

I studied digital forensics and how investigators collect, preserve, and analyse evidence from computer systems.

**Key learning points:**

- Understanding the purpose of digital forensic investigations.
- Learning the importance of evidence integrity.
- Understanding chain of custody.
- Identifying common sources of digital evidence.
- Learning the difference between volatile and non-volatile data.
- Understanding the role of file hashes and metadata.
- Recognizing why forensic analysis should avoid unnecessarily modifying original evidence.

**Digital forensic evidence:**

| Evidence Type | Examples |
|---|---|
| Disk Evidence | Files, deleted files, partitions, filesystem metadata |
| Memory Evidence | Running processes, active connections, in-memory artifacts |
| Network Evidence | Packet captures, DNS requests, connection logs |
| System Logs | Authentication events, system changes, application activity |
| File Metadata | Timestamps, file size, permissions |
| Browser Artifacts | History, downloads, cached information |

**Important forensic concepts:**

- **Chain of custody:** Documentation of who collected, handled, transferred, and analysed evidence.
- **Evidence integrity:** Ensuring evidence remains unchanged and verifiable.
- **Hashing:** Generating a digest that can help verify file integrity.
- **Metadata:** Information describing a file or digital object.
- **Volatile data:** Information that may disappear when a system loses power.

**Linux forensic commands studied:**

```bash
file evidence.bin
stat evidence.bin
sha256sum evidence.bin
```

**Command explanations:**

- `file` identifies the probable file format.
- `stat` displays file metadata, including size and timestamps.
- `sha256sum` calculates a SHA-256 hash that can be recorded for integrity verification.

**Example integrity verification:**

```bash
sha256sum evidence.bin
sha256sum evidence-copy.bin
```

If the hashes match, the files are highly likely to have identical contents.

**Windows forensic commands:**

```powershell
Get-FileHash .\evidence.bin -Algorithm SHA256
Get-Item .\evidence.bin | Format-List *
```

These commands calculate a file hash and display file properties.

**Security takeaway:** Digital forensics requires a methodical approach to evidence collection, preservation, verification, and analysis. Evidence integrity is essential for reliable investigative conclusions.

| Stage | Purpose |
|---|---|

**Illustrative incident response scenario:**

The security team may:

1. Record the report and preserve the original message.
2. Examine email headers, sender details, and attachment indicators.
3. Determine whether the attachment was opened.
4. Review endpoint and authentication logs.
5. Contain affected systems if compromise is suspected.
6. Remove confirmed malicious artifacts through approved procedures.
7. Restore normal operations and monitor for recurrence.
8. Document findings and recommend improvements.

**Security takeaway:** Incident response is not only about stopping an attack. It also involves preserving evidence, minimizing business disruption, recovering safely, and preventing similar incidents.

Windows Event ID `4625` represents a failed logon event.

**Example SIEM workflow:**

```text
Servers / Endpoints / Firewalls
             |
             v
       Log Collection
             |

    Parsing & Normalization
             |

             |
             v
       Detection Rules
             |
             v
        Security Alert
             |
             v
      SOC Investigation
             |
             v
     Escalation / Response
```

**Practical example — Detecting repeated failed logins**

An organization wants to identify accounts experiencing unusually high numbers of failed authentication attempts.

A conceptual SIEM detection rule might be:

```text
IF failed_login_count >= 5
AND time_window <= 5 minutes
THEN generate_alert
```

The analyst would then investigate the affected account, source IP addresses, timestamps, successful logins following the failures, and whether the activity could represent password spraying or another authentication threat.

**Example Splunk SPL query:**

```spl
index=security EventCode=4625
| bin _time span=5m
| stats count AS failed_logins BY _time, Account_Name, Source_Network_Address
| where failed_logins >= 5
| sort - failed_logins
```

**Command explanation:**

- `index=security` searches a sample security index.
- `EventCode=4625` selects Windows failed-logon events.
- `bin _time span=5m` groups events into five-minute intervals.
- `stats count` counts events by time, account, and source IP.
- `where failed_logins >= 5` filters groups with at least five failed logons.

Field names vary depending on the log source and SIEM configuration. This is an illustrative query, not a verified result from a specific lab.

**Security takeaway:** SIEM platforms improve security visibility by transforming large volumes of log data into actionable alerts and investigation evidence.

**Firewall types:**

| Firewall Type | Description |
|---|---|
| Packet-Filtering Firewall | Filters packets using IP addresses, ports, and protocols |
| Stateful Firewall | Tracks connection state when making filtering decisions |
| Host-Based Firewall | Protects an individual computer or server |
| Network Firewall | Controls traffic between networks |
| Next-Generation Firewall | Combines traditional filtering with additional inspection and security features |
| Web Application Firewall | Inspects HTTP/HTTPS traffic to protect web applications |

**Example firewall decision process:**

```text
Incoming Network Packet
          |
          v
  Examine Source / Destination
          |
          v
  Check Protocol and Port
          |
          v
     Evaluate Rules
          |
     +----+----+
     |         |
   Allow      Deny
     |         |
     v         v
 Forward     Block
 Traffic     Traffic
```

**Linux firewall commands studied:**

```bash
sudo ufw status verbose
sudo ufw status numbered
```

These commands display firewall status and configured rules on systems using UFW.

**Example — Allowing SSH in an authorized lab:**

```bash
sudo ufw allow 22/tcp
```

This creates a rule allowing inbound TCP traffic on port 22. In a production environment, SSH access should be restricted to approved sources wherever possible.

**Example — Restricting SSH to a trusted administrative address:**

```bash
sudo ufw allow from 192.0.2.10 to any port 22 proto tcp
```

This permits SSH connections from the specified example address.

**Windows Firewall inspection:**

```powershell
Get-NetFirewallProfile
Get-NetFirewallRule -Enabled True |
    Select-Object -First 10 DisplayName, Direction, Action
```

These commands display firewall profile settings and a sample of enabled firewall rules.

**Important ports reviewed:**

| Port | Common Service |
|---|---|
| 22 | SSH |
| 53 | DNS |
| 80 | HTTP |
| 443 | HTTPS |
| 3389 | Remote Desktop Protocol |
| 445 | SMB |

**Security takeaway:** Firewalls reduce unnecessary network exposure by enforcing traffic restrictions, but they must be properly configured, reviewed, and monitored to remain effective.

#### C. IDS Fundamentals

I studied Intrusion Detection Systems (IDS) and how they identify potentially malicious activity on networks and endpoints.

**Key learning points:**

- Understanding the purpose of an IDS.
- Learning the difference between IDS and IPS.
- Understanding network-based and host-based intrusion detection.
- Recognizing signature-based and anomaly-based detection methods.
- Understanding how IDS alerts help identify suspicious activity.
- Learning about false positives and false negatives.
- Recognizing the importance of tuning detection rules.
- Understanding how IDS alerts can be forwarded to a SIEM.

**IDS and IPS comparison:**

| Feature | IDS | IPS |
|---|---|---|
| Main Purpose | Detect suspicious activity | Detect and prevent suspicious activity |
| Typical Operation | Passive monitoring | Inline inspection |
| Alerts | Yes | Yes |
| Blocking | Generally no | Yes, when configured |
| Operational Risk | Alert noise | Legitimate traffic may be blocked |

**Detection methods:**

**Signature-based detection**

Identifies activity matching known patterns associated with attacks or malicious behaviour.

**Anomaly-based detection**

Identifies activity that differs from established or expected patterns.

**Examples of IDS technologies:**

- Snort
- Suricata
- Zeek, which is primarily a network security monitoring and analysis platform
- Wazuh, which provides host-based detection and security monitoring capabilities

**Example IDS workflow:**

```text
Network Traffic
      |
      v
Traffic Inspection
      |
      v
Detection Rules / Behaviour Analysis
      |
      v
Suspicious Pattern Identified
      |
      v
Generate Security Alert
      |
      v
Forward to SIEM / Analyst
      |
      v
Investigate and Respond
```

**Practical example — Inspecting traffic with Suricata**

Example command for an authorized lab packet capture:

```bash
sudo suricata -r sample.pcap \
  -l ./suricata-output
```

This processes a packet capture file using the configured Suricata rules and writes output to the specified directory.

**Example — Reading generated alerts:**

```bash
cat ./suricata-output/fast.log
```

If the configured rules produce alerts, this file may contain information such as the alert signature, severity, source IP, destination IP, and protocol.

**Example Suricata rule for a controlled lab:**

```text
alert icmp any any -> any any (msg:"LAB ICMP traffic detected"; sid:1000001; rev:1;)
```

This illustrative rule generates an alert for matching ICMP traffic. It demonstrates signature structure rather than detecting a specific attack.

**Rule components:**

- `alert` — generate an alert.
- `icmp` — inspect ICMP traffic.
- `any any` — match any source and destination address or port fields.
- `msg` — alert description.
- `sid` — unique signature identifier.
- `rev` — rule revision.

**Security takeaway:** Intrusion detection provides visibility into suspicious activity, but effective detection depends on appropriate rules, reliable data sources, and analyst interpretation.

**Example — Basic service discovery with Nmap:**

```bash

```

**Command explanation:**

- `nmap` launches the network scanning tool.
- `-sV` attempts to identify service versions.
- `192.0.2.10` represents an assigned training target.

Service discovery can provide useful information for vulnerability assessment, but it does not by itself confirm that a service is vulnerable.

**Example — Reviewing a vulnerability finding:**

```text

Severity: High (illustrative)

```

**CVSS severity ranges:**

| CVSS Score | Severity |
|---|---|

I learned that CVSS is useful for estimating technical severity, but remediation priority should also consider exploitability, asset importance, exposure, and business impact.

**Security takeaway:** Vulnerability scanners help organizations identify weaknesses systematically, but scan results require validation, risk-based prioritization, remediation, and follow-up verification.
